# خطة تنفيذ Orax Remote — Cloudflare Workers + D1

> **هذه خطة للاعتماد، لا تنفيذ.** لم يُعدَّل أي كود، ولم يُنشأ أي مورد Cloudflare، ولم يُنشر شيء.
> الأساس: [CLOUDFLARE_ARCHITECTURE_AUDIT.md](CLOUDFLARE_ARCHITECTURE_AUDIT.md) (المرحلة الأولى).
> تاريخ الخطة: 2026-10-17. الحدود الرسمية المستخدمة هي حدود يوم التحقق (Workers Free: 100k طلب/يوم،
> 10 ms CPU؛ D1 Free: 5M صف مقروء/يوم، 100k صف مكتوب/يوم، 5 GB).

## 0. الرد على المتطلبات الخمسة في سطر واحد لكل منها

| المتطلب | كيف تُحققه هذه الخطة | الضمانة |
|---|---|---|
| الأمان | توقيع ed25519 على كل طلب إداري، تشفير الدعوات في D1، رموز إبطال مُهشَّرة، حدود صارمة للمدخلات، لا أسرار في السجلات | مصفوفة اختبارات أمنية T1–T18 (§9.4) |
| سرعة الاستجابة | مسار الرمز = طلب واحد إنشاء + طلب واحد استهلاك؛ لا نبضات؛ لا استعلام في مسار الجلسة | أهداف P50/P95 مع طريقة قياس (§8) |
| استقرار الجلسات | السجل **خارج** مسار الجلسة نهائيًا؛ انقطاع Worker/D1 لا يمس جلسة قائمة، والسقوط الآمن = دعوة كاملة | اختبار الفوضى (§9.6)، معيار A6 |
| تقليل التكلفة | بلا كتابة دورية، تنظيف مجدول فقط، استعلامات بفهارس، تقدير لثلاثة أحجام | §10 بنموذج حسابي وحدود تنبيه |
| لا بيانات شاشة عبر الخادم | لا endpoint يقبل وسائط؛ الجسم ≤ 16 KB؛ المخطط لا يحوي عمودًا لإطار أو إدخال؛ iroh P2P كما هو | اختبار بنيوي + مراجعة مخطط (§7) |

**دعم P2P:** لا يتغير. Worker لا يرى ولا يستطيع رؤية إطارات الشاشة أو الإدخال؛ يتبادل فقط
`Invitation` (عنوان + سرّ 32 بايت) مشفّرة أثناء التخزين. الاتصال يبقى QUIC مباشرًا أو عبر relay.

## 1. النطاق وغير الأهداف

**داخل النطاق (v1):**

1. سجل أجهزة دائم (تسجيل، بحث، إبطال) مبني على مفتاح ed25519 القائم في iroh.
2. خدمة إشارات بديلة لـ `boundary-codes` (رمز 12 رقمًا، استهلاك لمرة واحدة) مع تخزين دائم في D1.
3. مصادقة طلبات بتوقيع الجهاز نفسه (بلا حساب، بلا كلمة مرور، بلا سرّ في العميل).
4. عميل Rust في المشروع، خلف إعداد، بخيار السقوط إلى الدعوة الكاملة.
5. اختبارات ووثائق ونشر staging قابل للتكرار — عند اعتماد منفصل.

**خارج النطاق صراحةً:**

- لا Durable Objects، لا KV، لا R2، لا Queues في v1 (لا مبرر تقني؛ يُعاد النظر عند إضافة حضور حيّ).
- لا حسابات مستخدمين، لا تسجيل دخول، لا بريد، لا PII.
- لا نقل لأي بيانات جلسة، لا TURN، لا SFU، لا بديل عن iroh relay.
- لا استبدال لدليل n0 أو بروتوكول iroh، ولا تغيير في `wire.rs` أو ALPN أو صيغة `Invitation`.
- لا إلغاء اشتراك/فوترة، ولا إدارة مؤسسات.

## 2. القرارات المعمارية (ADR مختصرة)

| # | القرار | السبب | البديل المرفوض |
|---|---|---|---|
| D1 | معرّف الجهاز = مفتاح ed25519 العام (`EndpointId`) | يجعله غير قابل للانتحال بالمعرفة، ويستفيد من إثبات الملكية في iroh | معرّف عشوائي + `public_key` منفصل: يفتح باب انتحال معرّف مسروق |
| D2 | تسجيل الجهاز = طلب موقّع بالمفتاح نفسه | إثبات الملكية دون إرسال أي سرّ | كلمة مرور/رمز تسجيل: سرّ إضافي يجب حمايته |
| D3 | مساحة فصل للتوقيع: `orax-device-auth-v1` | منع إعادة استخدام التوقيع في سياق آخر (نفس المفتاح يوقّع مصافحة iroh) | توقيع الرسالة الخام: قابل لإعادة الاستهداف |
| D4 | تشفير الدعوة AES-256-GCM بمفتاح Worker قبل كتابتها في D1 | نسخة D1/تصديرها لا تكفي لاختطاف جلسة | نص صريح في D1 (كما في الذاكرة اليوم) |
| D5 | رمز الإبطال يُخزَّن كـ SHA-256 فقط | نفس منطق كلمات المرور: لا سرّ قابل للاستخدام في القاعدة | تخزين الرمز الخام |
| D6 | استهلاك الرمز عبر `UPDATE … WHERE consumed_at IS NULL` وفحص `meta.changes` | ذرّي بلا حاجة إلى `RETURNING` (تحقق إضافي في المرحلة 3)، وقابل للتنفيذ في استعلام واحد | `SELECT` ثم `DELETE` بلا شرط: سباق يسمح باستهلاك مزدوج |
| D7 | لا تخزين لعنوان الجهاز في السجل (v1) | العنوان من iroh/N0 أو من الدعوة؛ تخزينه يعني كتابات دورية ومركزية بيانات وصفية | «دليل عناوين» في D1: 24 كتابة/يوم/جهاز ⇒ سقف ~4,100 جهاز ومركزية أعلى |
| D8 | لا نبضات كتابة (heartbeat معطّل افتراضيًا) | 288 كتابة/يوم/جهاز تقصّف الحد المجاني | نبضة كل 5 دقائق |
| D9 | لا endpoints لقبول/رفض الاتصال | الموافقة تحدث داخل جلسة iroh المشفّرة؛ إدخال الخادم فيها يخلق طرفًا ثالثًا قادرًا على الموافقة | `/sessions/accept`: يمنح الخادم سلطة لا يجب أن يملكها |
| D10 | خدمة `boundary-codes` (axum) تبقى | استضافة ذاتية/محلي/اختبارات، ولا كسر للمستخدمين الحاليين | حذفها: يكسر نشرًا قائمًا |
| D11 | النشر أحادي المستأجر في v1 | أبسط أمنًا وتكلفة؛ العنوان قابل للتخصيص أصلًا في العميل | multi-tenant: يحتاج هوية مستأجر وسياسات أعقد |
| D12 | رمز الإلغاء + إعادة التسجيل بالمفتاح الجديد كمسار استعادة | لا يضعف الهوية (لا استعادة بكلمة مرور) | استعادة بالبريد: يحتاج PII وحسابات |

## 3. البنية الهدف وتدفّق البيانات

```
المضيف (DeskVNC Support)                            المساعد (DeskVNC)
┌──────────────────────────────┐                  ┌──────────────────────────────┐
│ boundary-session::host        │                  │ boundary-session::viewer      │
│ machine.key (ed25519)         │                  │ boundary-helper.key (ed25519) │
└───────┬──────────────────────┘                  └───────┬──────────────────────┘
        │ (1) POST /v1/signals  موقّع                       │
        │     {invitation} ──────────────────────────────► │
        │                                        ┌─────────┴─────────┐
        │                                        │ Cloudflare Worker │
        │                                        │  + D1 (مشفّر)     │
        │                                        └─────────┬─────────┘
        │ (2) يعرض الرمز 1234 5678 9012                   │
        │                                    (3) POST /v1/signals/resolve {code}
        │                                        └──────────► {invitation}
        │
        │ (4) iroh/QUIC مباشر أو relay — لا يمرّ عبر Worker
        └───────────────────────────────────────────────────────────────►
```

**الضمانات البنيوية:**

- لا يوجد في المخطط أي عمود ثنائي كبير أو حقل «frame/input/clipboard».
- حدّ جسم الطلب 16 KB، والدعوة نفسها ≤ 4 KB مشفّرة.
- الـ Worker لا يستطيع الموافقة على جلسة، ولا حقن إدخال، ولا فك تشفير وسائط (لا يراها).
- الحد الأقصى لما يمكن أن يتسرّب من قاعدة البيانات = عنوان جهاز + سرّ جلسة غير مستهلكة، مشفّرًا
  بمفتاح Worker (D4)، لعمر ≤ 10 دقائق.

## 4. عقد API v1

الأساس: `https://<host>/v1` — كل الاستجابات JSON، `Content-Type: application/json; charset=utf-8`،
`Cache-Control: no-store`، `X-Content-Type-Options: nosniff`. لا CORS (عميل سطح مكتب فقط؛ لا تُستخدم
CORS كمصادقة).

### 4.1 ترويسات المصادقة (كل الطلبات الإدارية)

```
X-Orax-Device:     <EndpointId hex>               (64 حرفًا: 0-9a-f)
X-Orax-Timestamp:  <unix seconds>
X-Orax-Nonce:      <16 بايت base64url>            (22 حرفًا)
X-Orax-Signature:  <ed25519 base64url>            (86 حرفًا)
```

السلسلة الموقّعة (UTF-8، `\n` فاصلًا، بلا مسافات زائدة):

```
orax-device-auth-v1
POST
/v1/signals
sha256-hex(<body bytes>)
1770000000
Qm9yYXhOb25jZTEyMzQ1Ng
```

القواعد:

- `sha256(body)` يُحسب على البايتات المستقبَلة قبل أي إعادة ترميز.
- الجهاز يتحقق Worker من: صيغة hex (64 حرفًا صغيرًا)، تطابق `X-Orax-Device` مع المفتاح العام المضمّن في قاعدة البيانات
  (أو المفتاح المعلن في طلب التسجيل)، صحة التوقيع، وأن `|now − timestamp| ≤ 120` ثانية.
- منع الإعادة: عمود `auth_nonces` للطلبات **الحسّاسة فقط** (تسجيل، إبطال، إنشاء رمز) مع TTL 10 دقائق؛
  وطلبات القراءة تكتفي بنافذة الوقت.
- لا تُسجَّل الترويسات ولا الأجسام في السجلات؛ تُسجَّل فقط (method, path, status, ms, device_prefix).

### 4.2 نقاط النهاية

| # | الطريقة والمسار | المصادقة | الغرض | النجاح | الأخطاء |
|---|---|---|---|---|---|
| 1 | `POST /v1/devices` | توقيع بالمفتاح **الجديد** | تسجيل جهاز (أو إعادة تسجيل نفس المفتاح) | 201 جديد / 200 موجود | 400, 401, 403 (مُبطَل), 413, 409 (id غير مطابق للمفتاح), 429 |
| 2 | `GET /v1/devices/{id}` | لا شيء (بيانات عامة فقط) | البحث عن جهاز بالمعرّف | 200 | 400, 404, 429 |
| 3 | `POST /v1/devices/{id}/revoke` | توقيع الجهاز نفسه (أو رمز إدارة في ترويسة منفصلة) | إبطال الجهاز | 204 | 401, 403, 404 |
| 4 | `POST /v1/signals` | توقيع جهاز مُسجَّل وغير مُبطَل | إنشاء رمز دعوة | 201 | 400, 401, 403, 413, 429 |
| 5 | `POST /v1/signals/resolve` | لا شيء (الرمز نفسه هو القدرة) | استهلاك رمز لمرة واحدة | 200 | 400, 404 (غير موجود/مستهلك/منتهٍ), 429 |
| 6 | `POST /v1/signals/revoke` | رمز الإلغاء في الجسم | إلغاء رمز قبل استهلاكه | 204 (متكرر آمن) | 400, 404 |
| 7 | `POST /v1/devices/{id}/heartbeat` | توقيع الجهاز | آخر ظهور (اختياري، معطّل افتراضيًا) | 204 | 401, 403, 429 (فاصل أدنى 15 دقيقة) |
| 8 | `GET /healthz` | لا شيء | صحة الخدمة (SELECT 1) | 200 | 503 |

**ما لم نُنشئه ولماذا:** قبول/رفض/إلغاء الجلسة (D9)؛ «نبضة» إلزامية (D8)؛ تسجيل رمز وصول للجلسة
(السرّ داخل الدعوة)؛ أي endpoint ثنائي (شاشة/ملف/إدخال).

### 4.3 أمثلة العقود

**1) تسجيل جهاز**

```http
POST /v1/devices
X-Orax-Device: b3fx…q2
X-Orax-Timestamp: 1770000000
X-Orax-Nonce: Qm9yYXhOb25jZTEyMzQ1Ng
X-Orax-Signature: 9c1f…

{"public_key":"<base64url 32 بايت>","label":"Reception PC","client_version":"0.30.0","protocol_version":1}
```

```json
201 Created
{"id":"b3fx…q2","fingerprint":"sha256:…","created_at":1770000000,"revoked":false}
```

`id` يُحسب في Worker من `public_key` (نفس اشتقاق `EndpointId`)، وأي تعارض بين `X-Orax-Device` والمفتاح
يُرفض بـ 409. هذا يمنع «تسجيل معرّف يختاره العميل» نهائيًا.

> **تحقق إلزامي في P3:** يجب أن يطابق اشتقاق المعرّف في Worker مخرَج `EndpointId::to_string()` بايتًا
> ببايت (نفس صيغة hex الصغيرة التي ينتجها `EndpointId::to_string()`). يُثبت بمتجه مشترك في `cloudflare/test/fixtures/` (Rust ينتج
> لِمفتاح ثابت من بذرة معروفة، وWorker يعيد إنتاج نفس النص). عدم التطابق يوقف المرحلة.

**2) البحث**

```json
200 OK
{"id":"b3fx…q2","fingerprint":"sha256:…","protocol_version":1,"client_version":"0.30.0",
 "created_at":1770000000,"revoked_at":null}
```

**4) إنشاء رمز دعوة**

```json
{"invitation":"boundary1:eyJ2ZXJzaW9uIjox…","ttl_seconds":600}
```

```json
201 Created
{"code":"123456789012","expires_at":1770000600,"revoke_token":"<64 hex>"}
```

تحققات الخادم: JSON صالح، `version == 1`، `secret` بطول 32 بايت، `expires` في المستقبل و≤ 600 ثانية
من `now`، والحجم ≤ 4 KB. يُرفض ما عدا ذلك بـ 400 **قبل** أي كتابة.

**5) الاستهلاك** — `POST /v1/signals/resolve` بجسم `{"code":"1234 5678 9012"}` (تُطبَّع المسافات):

```json
200 OK
{"invitation":"boundary1:…"}
```

```json
404 Not Found
{"error":{"code":"not_found","message":"This code is not valid, has expired, or was already used"}}
```

**الاستهلاك ذرّي:** `UPDATE signal_codes SET consumed_at=? WHERE code=? AND consumed_at IS NULL AND
expires_at>?` ثم قراءة الصف فقط إذا كان `meta.changes == 1`؛ وإلا 404. لا يوجد سيناريو يستهلك فيه
طلبان الرمز نفسه.

**الحدود الثابتة:** جسم ≤ 16 KB (413 قبل التحليل)، `label` ≤ 64 حرفًا بلا محارف تحكم،
`client_version` ≤ 32، `ttl_seconds` ∈ [30, 600]، رمز 12 رقمًا، `revoke_token` 64 hex.

### 4.4 الأخطاء الموحّدة

| HTTP | code | متى |
|---|---|---|
| 400 | `bad_request` | JSON/حقل غير صالح، خارج الحدود |
| 401 | `unauthorized` | توقيع/زمن/إعادة إرسال/جهاز غير معروف |
| 403 | `forbidden` | جهاز مُبطَل، أو محاولة إدارة جهاز آخر |
| 404 | `not_found` | جهاز/رمز غير موجود أو منتهٍ أو مستهلَك |
| 409 | `conflict` | تداخل معرّف/مفتاح، أو إعادة تسجيل بحالة مختلفة |
| 413 | `payload_too_large` | جسم > 16 KB |
| 429 | `rate_limited` | تجاوز حد؛ مع `Retry-After` |
| 503 | `unavailable` | فشل D1/صيانة؛ مع `Retry-After` |

لا تُعاد أبدًا تفاصيل داخلية (رسائل D1، stack traces، قيم ترويسات).

## 5. مخطط D1 (مسودة المرحلة 2 — القابلة للتنفيذ بعد الاعتماد)

```sql
-- migrations/0001_init.sql  (قابل لإعادة التنفيذ بأمان)
CREATE TABLE IF NOT EXISTS schema_meta (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS devices (
  id               TEXT PRIMARY KEY CHECK (length(id) = 64 AND id NOT GLOB '*[^0-9a-f]*'),
  public_key       BLOB NOT NULL CHECK (length(public_key) = 32),
  fingerprint      TEXT NOT NULL CHECK (length(fingerprint) = 64),
  label            TEXT CHECK (label IS NULL OR length(label) <= 64),
  client_version   TEXT CHECK (client_version IS NULL OR length(client_version) <= 32),
  protocol_version INTEGER NOT NULL DEFAULT 1 CHECK (protocol_version BETWEEN 1 AND 255),
  created_at       INTEGER NOT NULL,
  updated_at       INTEGER NOT NULL,
  last_seen_at     INTEGER,
  revoked_at       INTEGER,
  replaced_by      TEXT CHECK (replaced_by IS NULL OR length(replaced_by) = 64)
);
CREATE INDEX IF NOT EXISTS devices_revoked_idx   ON devices(revoked_at) WHERE revoked_at IS NOT NULL;
CREATE INDEX IF NOT EXISTS devices_last_seen_idx ON devices(last_seen_at);

CREATE TABLE IF NOT EXISTS signal_codes (
  code         TEXT PRIMARY KEY,
  ciphertext   BLOB NOT NULL CHECK (length(ciphertext) BETWEEN 1 AND 4096),
  nonce        BLOB NOT NULL CHECK (length(nonce) = 12),
  host_id      TEXT NOT NULL,
  auth_nonce   TEXT NOT NULL,                -- مفتاح إعادوية إعادة المحاولة
  created_at   INTEGER NOT NULL,
  expires_at   INTEGER NOT NULL,
  consumed_at  INTEGER,
  revoke_hash  BLOB NOT NULL CHECK (length(revoke_hash) = 32),
  UNIQUE (host_id, auth_nonce),
  -- 12 رقمًا. نفي صنف واحد بدل 12 صنفًا: SQLite في workerd يرفض النمط الطويل
  -- بـ "LIKE or GLOB pattern too complex" (تحقق فعلي في P2)، وهذا الشكل يعمل على D1 وnode:sqlite معًا.
  CHECK (length(code) = 12 AND code NOT GLOB '*[^0-9]*')
);
CREATE INDEX IF NOT EXISTS signal_codes_expiry_idx ON signal_codes(expires_at);
CREATE INDEX IF NOT EXISTS signal_codes_host_idx   ON signal_codes(host_id, created_at);

CREATE TABLE IF NOT EXISTS auth_nonces (
  nonce      TEXT PRIMARY KEY,
  device_id  TEXT NOT NULL,
  expires_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS auth_nonces_expiry_idx ON auth_nonces(expires_at);

CREATE TABLE IF NOT EXISTS audit_events (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  at        INTEGER NOT NULL,
  kind      TEXT NOT NULL CHECK (length(kind) <= 32),
  device_id TEXT,
  detail    TEXT CHECK (detail IS NULL OR length(detail) <= 128)
);
CREATE INDEX IF NOT EXISTS audit_events_at_idx ON audit_events(at);
```

**مبررات كل جدول/فهرس:** `devices` صف واحد لكل هوية (المعرّف هو المفتاح، فلا ازدواج ممكن)؛
`signal_codes` يحمل حمولة **مشفّرة** + بصمة الإلغاء + حالة الاستهلاك؛ `UNIQUE(host_id, auth_nonce)`
يجعل إعادة المحاولة بعد انقطاع الشبكة **إعادوية** بدل إنشاء رمزين؛ فهارس `expires_at` للتنظيف
المجدول، و`host_id, created_at` لسياسة الحد لكل جهاز؛ `auth_nonces` للإعادة فقط؛ `audit_events`
بلا أي محتوى جلسة وباحتفاظ ≤ 30 يومًا.

**تنظيف مجدول (Cron Trigger، كل 15 دقيقة):**

```sql
-- كل عبارة تُنفَّذ منفصلة بمعاملاتها؛ D1 لا يشارك المعاملات بين العبارات.
-- المعاملات الموضعية `?` متعمَّدة (بدل ?1) لتبقى نفسها في Worker وفي اختبارات node:sqlite.
DELETE FROM signal_codes WHERE rowid IN (
  SELECT rowid FROM signal_codes WHERE expires_at < ? OR consumed_at < ? LIMIT 500
);
DELETE FROM auth_nonces WHERE rowid IN (
  SELECT rowid FROM auth_nonces WHERE expires_at < ? LIMIT 500
);
DELETE FROM audit_events WHERE rowid IN (
  SELECT rowid FROM audit_events WHERE at < ? LIMIT 500
);
```

كل صف محذوف = صف مكتوب واحد، ويُحسب في نموذج الكلفة (§10).

**الاحتفاظ:** `audit_events` 30 يومًا؛ `signal_codes` تُحذف عند الاستهلاك أو الإلغاء أو انتهاء الصلاحية
+ 1 ساعة كحد أقصى؛ `devices` تبقى حتى الإبطال (مع `revoked_at`، وحذف كامل عند طلب صريح من مالك الجهاز).

## 6. الأمان: الضوابط الملموسة

| التهديد (من التدقيق) | الضابط في هذه الخطة | اختبار |
|---|---|---|
| S1/S2 سرّ الجلسة في القاعدة | AES-256-GCM بمفتاح Worker (`env.INVITATION_KEY`، سرّ 32 بايت) + AAD = `code‖expires_at` + حذف عند الاستهلاك + TTL ≤ 600s | T16, T19 |
| S3 مخزن في الذاكرة | D1 دائم + استهلاك ذرّي | T7, T8 |
| S4 لا إبطال مركزي | `revoked_at` + رفض كل عملية لجهاز مُبطَل + إبطال ذاتي موقّع | T12 |
| تسريب الأسرار في السجلات | لا تسجيل لأجسام/ترويسات؛ مرشّح حقول قبل التسجيل | T15 |
| إعادة إرسال | نافذة ±120s + nonce للعمليات الحساسة | T3, T4 |
| انتحال معرّف | الاشتقاق من المفتاح + رفض التعارض 409 | T1b |
| حقن SQL | استعلامات مُعدّة (prepared) بمعاملات فقط، لا تركيب نصي | T11 |
| استنزاف الحصة | حدود لكل جهاز/لكل IP + سقف عالمي + تنبيهات | T10, §10 |
| إغراق الأجسام | 413 قبل التحليل + حدود حقول | T5 |
| تعداد الأجهزة | `GET /devices/{id}` يعيد حقولًا دنيا فقط، ومعدّل محدود؛ لا قائمة أجهزة في v1 | T2b |
| تلاعب بالحمولة | GCM يفشل مغلقًا → 404 لا 500 | T16 |
| سرقة مفتاح الجهاز | خارج نطاق الخادم؛ التخفيف في العميل (keychain) — تدقيق S6 | مراجعة |

**نموذج الثقة المعلن:** الـ Worker **طرف موثوق** للرمز أثناء صلاحيته (يستطيع تشفير/فك تشفير الدعوة،
وبالتالي يستطيع نظريًا إعادة توجيه مساعد إلى مضيف مهاجم). ما لا يستطيعه: الموافقة، قراءة الشاشة،
حقن إدخال، فك تشفير الجلسة (iroh E2E)، إنشاء جلسة بلا موافقة الشخص. تُوثَّق هذه الحدود في
`docs/SECURITY_MODEL.md` وتُخفَّض بأقل نطاق بيانات ممكن.

**أسرار الخدمة:** مفتاح التشفير في Cloudflare Secrets فقط (لا متغيّر عام، لا Git). يُدعم دوران
(مفتاح جديد + `key_id` في الصف) دون فقدان رموز قائمة عبر إعادة تشفير تدريجية.

## 7. ضمان «لا بيانات جلسة عبر الخادم» (قابل للفحص آليًا)

1. لا endpoint يقبل `application/octet-stream` أو وسائط؛ كل الأجسام JSON ≤ 16 KB.
2. اختبار بنيوي على المخطط: يفشل إن ظهر عمود باسم/نوع يشبه `frame|pixel|image|input|clipboard|audio`.
3. اختبار على الـ Worker: يفشل إن استقبل طلبًا > 16 KB أو `Content-Type` غير JSON.
4. مراجعة `boundary-session`: الجلسة تُفتح عبر iroh فقط، ولا يظهر عميل HTTP داخل `serve()`.
5. **قاعدة سلوكية:** لا يُستدعى أي endpoint أثناء جلسة نشطة (لا في مسار إطار/حركة/ضغطة مفتاح).

## 8. الأداء: أهداف أولية وطريقة قياس (لا ادّعاء قبل القياس)

| المقياس | هدف أولي | طريقة القياس |
|---|---|---|
| CPU لكل طلب (Free plan) | P95 ≤ 5 ms (سقف 10) | `wrangler tail` → `cpuTime`، 1000 طلب مختلط |
| `POST /v1/signals` P95 | ≤ 150 ms من EU/US، ≤ 350 ms من آسيا | سكربت من 3 مناطق، 500 تكرار، تقرير P50/P95/P99 |
| `POST /v1/signals/resolve` P95 | ≤ 120 ms (منطقتان) | نفس الأسلوب |
| `GET /v1/devices/{id}` P95 | ≤ 100 ms | نفس الأسلوب |
| أثـر السجل على بدء الجلسة | ≤ 1 RTT إضافي قبل مصافحة iroh؛ صفر أثناء الجلسة | قياس فاصل: زمن الرمز مقابل زمن أول إطار |
| زمن اكتشاف انقطاع المضيف | لا يتغير (مهلة QUIC/قراءة 5s القائمة) | اختبار انقطاع |

`/healthz` يتجاوز `SELECT 1`، لا قراءة/كتابة في مسار الإطارات، ومراقبة `rows_read/written` من
`meta` في كل استجابة أثناء التطوير.

### 9.3 اختبارات العميل (Rust)

- اشتراك متجهات التوقيع بين Worker وRust (`cloudflare/test/fixtures/signing.json`): نفس المدخلات ⇒
  نفس التوقيع byte-for-byte.
- اشتراك متجه اشتقاق المعرّف (`cloudflare/test/fixtures/device-id.json`): مفتاح عام ثابت ⇒ نفس
  `EndpointId` في Rust وTypeScript.

- السقوط الآمن: فشل السجل ⇒ مسار الدعوة الكاملة بلا حجب الواجهة.
- عدم وجود أسرار في التصور (Debug) للطلبات.

### 9.4 سيناريوهات الاعتمادية (من خطة المشروع §9)

تثبيت جهاز جديد؛ إعادة تشغيل مع بقاء المعرّف؛ تغيّر IP؛ انقطاع الإنترنت وعودته؛ إعادة تسجيل؛ انتهاء
الصلاحية؛ إلغاء جهاز؛ محاولة انتحال معرّف؛ مفتاح خاطئ؛ طلب مكرر/قديم؛ مدخلات ضخمة؛ تجاوز المعدل؛
تعطل D1 مؤقتًا؛ تعطل API؛ انقطاع التنسيق أثناء محاولة اتصال؛ رفض المستخدم؛ محاولات متزامنة.
**في كل سيناريو:** جلسة قائمة لا تتأثر، والمسار الكامل يظل ممكنًا عبر الدعوة الكاملة.

### 9.5 اختبار الفوضى (staging)

| الحقن | المتوقع |
|---|---|
| Worker يعيد 503 لكل الطلبات | إنشاء الرمز يفشل برسالة واضحة + عرض الدعوة الكاملة؛ جلسة قائمة سليمة |
| D1 يرفض الكتابة (quota) | 503 لا 500؛ العميل لا يعيد بلا نهاية |
| resolve يعيد 429 | الرسالة تفيد «حاول مجددًا بعد X» وتُبقي الدعوة معروضة للمضيف |

| Worker بطيء (500ms) | المهلة في العميل (3s) لا تجمّد الواجهة |

### 9.6 E2E حقيقي (شرط قبول لا يُستبدل)

جهازان، شبكتان مختلفتان (خلف NAT مختلف): إنشاء رمز على A، إدخاله على B، الموافقة على A، تحقق نقل
الشاشة والإدخال، ثم قتل Worker وإعادة المحاولة. تُسجَّل النتائج (تواريخ، إصدارات، مسارات مباشر/relay).

## 10. الكلفة والحدود

**افتراضات معلنة:** جلسة دعم = `POST /v1/signals` + `POST /v1/signals/resolve` (+ إلغاء/انتهاء) ⇒
≈ 3 طلبات، ≈ 3 صفوف كتابة، ≈ 2 صفوف قراءة. تسجيل جهاز مرة واحدة. لا نبضات. تنظيف مجدول يضيف
≈ 1 كتابة لكل رمز منتهٍ.

| الحجم | أجهزة | جلسات/يوم | طلبات/يوم | كتابات/يوم | قراءات/يوم | مقابل الحد المجاني |
|---|---|---|---|---|---|---|
| صغير | 10 | 20 | ~80 | ~120 | ~100 | < 1% |
| مئات | 500 | 200 | ~650 | ~1,000 | ~1,500 | ~1% |
| آلاف | 5,000 | 2,000 | ~6,000 | ~10,000 | ~20,000 | 6% طلبات، 10% كتابات |

**الحدود الحاكمة:** الطلبات (100k/يوم) ثم الكتابات (100k/يوم). **نبضة كل 5 دقائق** لكل 5,000 جهاز =
1.44M كتابة/يوم ⇒ تجاوز 14×، لذلك منع النبضات قرار تصميمي لا تحسين.

**حماية من الاستنزاف:** حد إنشاء رموز لكل جهاز (20/ساعة، يتم عبر استعلام فهرس `host_id, created_at`)،
حد حل لكل IP (20/دقيقة best-effort داخل الـ isolate)، سقف حجم، وإلغاء تلقائي للرموز. تنبيهات عند 60%
و80% من طلبات/كتابات D1. **حد عالمي دقيق** بعدّادات مشتركة يحتاج Durable Object (مدفوع) — يُؤجَّل مع
توثيق الخطر المتبقي، ويُخفَّف بـ WAF Rate Limiting إن كان متاحًا في الخطة.

**خطة الترقية:** Workers Paid (5$/شهر) + D1 مدفوع (25B قراءة و50M كتابة مشمولة) عند تجاوز الحدود،
مع إبقاء المعمارية كما هي بلا تغيير كود.

**الكلفة الخارجة عن Cloudflare:** iroh public relays مجانية محدودة المعدل؛ Pro 19$/شهر عند الحاجة
(100 GB خروج، 10k اتصال). لا تُغيَّر في هذه الخطة.

## 11. تكامل العميل (بأقل تعديل)

**crate جديدة `crates/orax-registry/`:** عميل HTTP + توقيع + نماذج JSON + أخطاء مُصنَّفة. تعتمد على
`reqwest`/`serde` من تبعيات الـ workspace، وعلى `iroh` (أو `ed25519-dalek` 3 الموجود في `Cargo.lock`)
لتوقيع ed25519، ولا تعتمد على Tauri.

**نقاط الحقن (كلها خلف إعداد، بلا تغيير سلوك افتراضي):**

| الملف | التغيير | ملاحظة |
|---|---|---|
| `src-tauri/src/commands/support.rs` | إنشاء الرمز عبر `orax-registry` إذا كان العنوان مهيأً، وإلا `boundary-codes` كما اليوم | `Model::publish_code` (307-321) |
| `src-tauri/src/commands/boundary.rs` | حل الرمز عبر السجل مع السقوط إلى `boundary-codes` | `connect_boundary` (70-110) |
| `Cargo.toml` + `src-tauri/Cargo.toml` | عضو جديد + تبعية | لا تغيير إصدارات |
| `ui/src/lib/support.ts` | إعداد عنوان السجل مستقلًا (مفتاح localStorage جديد) | الحقل القائم للرمز يبقى |
| `crates/boundary-app/src/codes.rs` | نفس التوجيه لتطبيق الدعم المستقل (المرحلة 5) | تكافؤ السلوك |

**غير معدَّل:** `boundary-session` (wire/session/unattended)، `boundary-codes` (يبقى)، ALPN، الإصدارات.

**نقطة تحقق إلزامية في المرحلة 5:** هل يوفّر `iroh::SecretKey` توقيعًا خامًا
(`sign(&[u8]) -> [u8;64]`)؟ إن لم يوفّره، يُشتق مفتاح توقيع ed25519 منفصل في `orax-registry` مع ربط
موثّق بالمعرّف (لا يُنشأ سرّ جديد بلا حاجة). تُحسم باختبار قبل كتابة العميل.

**السقوط الآمن:** أي 5xx/429/مهلة ⇒ إظهار الدعوة الكاملة وإبقاء المسار القديم؛ لا حجب للواجهة، لا
إعادة بلا نهاية، ولا إعادة على 4xx.

## 14. المخاطر المتبقية (بعد هذه الخطة)

1. الـ Worker طرف موثوق للرمز أثناء صلاحيته (§6) — مخفَّض لا مُلغى.
2. حد المعدل العالمي الدقيق يحتاج DO مدفوع — مؤجَّل ومُوثَّق مع WAF كتخفيف.
3. D1 كتابة في منطقة واحدة: زمن إنشاء الرمز يتأثر بالموقع الجغرافي (مقاس، لا مُقدَّر).
4. الهوية ملف على القرص بلا TPM (خارج نطاق هذه الخطة؛ بند S6 في التدقيق).
5. تعدّد المستخدمين على Windows ينتج هويات متعددة للجهاز المادي — السجل يعرضها كأجهزة منفصلة.
6. لا Toolchain Rust محليًا: تحقق Rust يكون في CI فقط.

## 15. قرارات مطلوبة قبل بدء P2

1. **نطاق v1:** دليل + رموز فقط (موصى) أم إضافة استعادة جهاز/نبضات اختيارية الآن؟
2. **العنوان والعقد:** Workers على نطاق خاص أم `workers.dev` للاختبار؟ ومن يملك الحساب والأسرار؟
3. **التشفير في D1:** تشفير AES-GCM بمفتاح Worker (موصى) أم بديل تفضّله؟
4. **التعديل في العميل:** إضافة crate + إعدادين (موصى) أم تأجيل ربط العميل بعد P4؟
5. **النشر:** تأكيد أن P6 يتوقف على موافقة منفصلة قبل إنشاء أي مورد Cloudflare.
6. **حدود مجانية:** هل نلتزم بحدود Free (موصى للبداية) أم نخطط لـ Paid من اليوم الأول؟

**بالاعتماد، أبدأ P2 فقط:** مجلد `cloudflare/` + `migrations/0001_init.sql` + اختبارات D1 محلية،
بلا أي نشر وبلا لمس `boundary-session`.
